# ADR 0024: Integration clients with bearer API keys, route-declared scopes and middleware idempotency

Status: Accepted · Date: 2026-11-17 · Phase 6a

## Context
Conclusion, ERP and Billing call the same `/api/v1` as the web frontend (FR-INT-01..12, API spec section 19). CLAUDE.md requires one policy function combining role, ownership and scopes, deny-by-default for integrations, keys shown once and stored only as hashes, cross-system IDs in `external_reference`, and no integration-only copies of business logic. Owner decisions (Phase 6): build on the section 19.9 read-only profiles; clients stay inactive until the data flow is confirmed (requirements open questions 7 and 8); per-client rate limit 300 per minute by default; key expiry 12 months by default, 24 at most; usage counters in PostgreSQL.

## Decision
- **One authenticator, two credentials.** `core.auth.combined_authenticator` uses the session cookie for people and `Authorization: Bearer` for integration clients; both at once is `400 auth.mixed_credentials`. The integration module resolves a key into a `Principal` of type `integration` that carries `client_id`, `system`, `scopes`, `default_owner_id` and `rate_limit_per_minute`; its `user_id` is the client's **service user** (`user_type = 'service'`, role `integration`), so audit entries, timelines and `created_by` name "ERP (integration)" without special cases.
- **Key format and storage.** `crm_<env>_<key_id>_<secret>`: the 16-hex `key_id` is the lookup column; only SHA-256 of the 256-bit secret is stored and compared with `hmac.compare_digest`. A plain hash, not a password hash, is right for a random 256-bit secret, and keeps each request cheap. At most two active keys per client for rotation; `last_used_at`/`last_used_ip` are written at most once a minute. The CIDR allowlist is checked against the client IP that the proxy-aware request context resolved.
- **Scopes on the route, checked by the policy.** `endpoint(AccessLevel.X, scope="…")` declares the scope next to the access level (ADR 0013) and publishes it as `x-required-scope`. A route without a scope is closed to integrations (`permission.not_for_integrations`), including Public routes. Two forms cover the shared routes: alternatives (`a|b`, any one suffices) and templates (`{resource}:read`, filled from path parameters). Services use `policy.has_scope` / `require_scope` where the needed scope depends on data (a resolved reference's record type, search types), and `policy.record_owner` to require a human owner on create (`422 owner.required`). After the scope check the `integration` role's rules apply as usual, so changing an owner, archive, assign and convert stay closed.
- **External references in the integration module, filters through a hook.** The integration module owns `external_reference` and `external_system`. Party and sales lists accept `external_system`, `external_id` and `has_external_reference` through `core.external`; the condition is supplied by the integration module, registered in `app.main` (ADR 0018), so lower modules never import it.
- **Idempotency and usage as ASGI middleware.** `IntegrationMiddleware` stores the first response to an integration `POST` carrying `Idempotency-Key` (per client, 24 h, fingerprint of method, path and body) and replays it with `Idempotent-Replayed: true`; a different body is `422 idempotency.key_reused`, a concurrent duplicate `409 idempotency.in_progress`, and `5xx` responses are not stored. It works for every route without touching them. It also counts each integration request (and each `4xx`/`5xx`) in an hourly `integration_usage` row, upserted outside the request transaction; the worker purges idempotency records after 24 h and usage after 30 days.
- **Rate limit per client.** The existing fixed-window limiter keys integrations by `client:<id>` with the client's own limit, so one system cannot use up another's budget.
- **Inactive by default.** `POST /integration-clients`, the admin UI and `python -m app.cli create-integration-client` create clients inactive; an Admin activates them after the owner confirms the flow.

## Consequences
- Every endpoint added later states its integration scope (or none) in one place; the generated authorization matrix tests all levels for people and integration clients, with all scopes and with none.
- A leaked key is limited by its scopes, the allowlist, expiry, rate limit and immediate revocation, and is never recoverable from the database or logs.
- Idempotency buffers the response body of covered requests in memory; create responses are small, so this is acceptable. Exports and imports, which could be large, are closed to integrations.
- OAuth 2.0 client credentials (API spec section 20) can be added later as another bearer authenticator that produces the same `Principal`.
