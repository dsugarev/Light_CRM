# ADR 0026: Assistant tool loop over the services, SSE streaming, and usage kept apart from chats

Status: Accepted · Date: 2026-11-18 · Phase 7a

## Context
FR-AI-01..08 and architecture section 8 ask for a streamed chat that answers from read-only tools running with the user's permissions, record context, drafts saved as notes only on an explicit click, a switch (`AI_ENABLED`), a per-user rate limit and daily token budget, and token usage recorded per request. ADR 0006 makes the assistant read-only; ADR 0007 routes every model call through LiteLLM, OpenRouter and Cerebras. Owner decisions (Phase 7): `litellm` pinned; `react-markdown` with `remark-gfm` for rendering (7b); streaming without a library; a usage table so deleting chats does not reset the budget; defaults of 200,000 tokens per user per day, about 8,000 history tokens and 60 seconds per model call; stop through a database flag; a scripted model for the end-to-end stack, refused in production.

## Decision
- **The model behind a protocol.** `app.llm.types` holds the `LLM` protocol (one streamed call yields `TextDelta`s, then one `Completed` with tool calls and usage) and `LLMUnavailableError`. `app.llm.client.LiteLLMClient` is the only importer of `litellm`; `app.llm.factory.create_llm` loads it only when the assistant is on, otherwise the backend never imports it. The import-linter contract forbids a direct `litellm` import anywhere else. Every failure of the call (provider error, network, the overall timeout) becomes `LLMUnavailableError` carrying only the exception's class name, never prompt or answer text.
- **LiteLLM's MCP path is skipped.** With tools present, LiteLLM 1.108 imports its MCP gateway handler, which needs the optional `mcp` package, so every call with tools failed with a connection error. We use no MCP tools; the client passes LiteLLM's own `_skip_mcp_handler=True`. A test runs the real client with tools against a scripted provider server, so an upgrade that changes this fails the suite.
- **LiteLLM's import-time side effects are switched off.** In its default `DEV` mode LiteLLM loads the nearest `.env` file into the process environment when imported, and it downloads a model price list. The client sets `LITELLM_MODE=PRODUCTION` and `LITELLM_LOCAL_MODEL_COST_MAP=True` before importing it, and turns message logging off. A test guards against the `.env` loading coming back.
- **Tools over the services.** `assistant.tools` defines the eight tools of section 8.3 as Pydantic argument models (unknown fields refused; the JSON schema is generated from them), each calling the owning module's public service functions (the same ones the REST endpoints call) after `check_access(principal, SIGNED_IN)`. Results are compact dictionaries with the record's type, ID and in-app URL, at most 25 rows, archived records excluded, contact email addresses and phone numbers left out. Errors (`invalid_arguments`, `unknown_tool`, a service's error code) go back to the model as data.
- **Tool loop in the service, streaming in its own session.** `prepare_message` runs every check that should be an ordinary HTTP error (switch, ownership, validation, rate limit, budget), stores the question and an empty `streaming` answer, and commits. `stream_answer` then yields the Server-Sent Events from a fresh database session (the request's session ends with the handler): up to 5 tool rounds, after which the model is called without tools and must answer. The record in view (FR-AI-03) is given to the model as a `get_record` call and result inserted before the question, so CRM text reaches the model only inside tool results; the system prompt says tool content is data.
- **Citations from tool results.** Records returned by tools in the turn are collected; those whose ID or name appears in the answer become `record_ref` events and are stored on the message.
- **What is stored.** `chat_message` keeps questions and answers, the tools called with their arguments, the cited records and token counts. Tool results are not stored, unlike the architecture's role `tool` rows: they would copy CRM data, including personal data later anonymized under GDPR, into chat history. History sent to the model is earlier questions and answers only, newest first up to `AI_HISTORY_TOKENS` (estimated at four characters per token).
- **Usage apart from chats.** `assistant_usage` has one row per answer (user, time, prompt and completion tokens, tool rounds, outcome). The daily budget sums it from midnight Europe/Sofia; deleting a conversation removes its messages but not its usage.
- **Stop.** `POST .../stop` sets `stop_requested` on the answer; the stream checks it at most every half second while text arrives and between tool rounds, then ends with `message_end` (`status: stopped`) and keeps the text so far. A browser that disconnects is treated the same way.
- **Audit without content.** Conversation create, rename and delete publish domain events (`chat_conversation.*`) with no title or text; messages are not audited (they change no CRM data). A saved note is an ordinary `activity.created`.
- **A scripted model for development and end-to-end tests.** `LLM_FAKE=true` selects `app.llm.fake.DemoLLM` in-process, which calls `pipeline_summary` or `search_opportunities` and answers from the result in the question's language; `#fail` simulates an outage. The settings refuse `LLM_FAKE` in production. Because the end-to-end stack runs with `ENV=production`, it uses `app.llm.fake_server` instead: an OpenAI-compatible server that streams the same script in the provider's format, reached through the optional `LLM_API_BASE` setting. The real LiteLLM client, tool loop and streaming through the proxy are then exercised with production settings. API tests use their own scripted fake.
- **Live evaluation on demand.** `backend/scripts/assistant_eval.py` seeds fictional data in a disposable database, asks 20 English and Bulgarian questions through the real API with the real model, and checks tools called, required and forbidden facts, and the answer's language. It is never part of CI; results are recorded in `docs/assistant-eval.md`.

## Consequences
- No new infrastructure: streaming uses FastAPI's `StreamingResponse`, and stop works across backend processes because it goes through PostgreSQL.
- Rate-limit and budget refusals are HTTP `429` responses before any stream starts, which the frontend handles like other errors; only provider failures appear inside the stream.
- One answer can exceed the remaining budget (the check is before the answer); the next request is then refused until the next day.
- Because tool results are not stored, reopening a conversation shows the tools used and cited records but cannot replay what the tools returned; a follow-up question calls the tools again with current data.
- The `ReadOnly` notice that pydantic raises for LiteLLM's own types is filtered in the test configuration only; it is harmless and not an error at runtime.
