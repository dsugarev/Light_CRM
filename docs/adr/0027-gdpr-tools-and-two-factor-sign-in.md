# ADR 0027: GDPR export and anonymization across modules; optional TOTP two-factor sign-in

Status: Accepted · Date: 2026-11-18 · Phase 8a

## Context
FR-ADM-04 asks for a JSON export of all personal data held about a contact and an irreversible anonymization that keeps commercial history. FR-AUTH-07 (should have) asks for optional TOTP two-factor sign-in, enforceable for Admins. Owner decisions (Phase 8): build two-factor sign-in with `pyotp` and a QR code (`qrcode.react`); anonymize the contact and linked leads, keep the audit log unchanged, and list free-text mentions (activity notes, assistant chats) in the export for manual review instead of editing them.

## Decision
- **GDPR as an extension point of the party module.** Personal data about a contact lives in several modules, and party cannot import them (module layering). Following ADR 0018, party defines `PersonalDataProvider` and `ContactAnonymizer`; `app.main` registers providers from sales (leads linked or with the same email, opportunities with the contact as primary contact), activity (linked activities, and activities whose subject or body mentions the name or email), integration (IDs in other systems), assistant (chat messages that mention the contact, with an excerpt) and audit (the number of entries kept), and the sales anonymizer.
- **What anonymization changes.** The contact's names become "Anonymized #<last six hex digits of the ID>"; email, phone, job title, preferred language and notes are cleared; `anonymized_at` is set. Linked leads and leads with the same email lose contact name, email and phone. Organization, opportunities, activities and their links stay. Anonymized contacts cannot be edited (`409 contact.anonymized`), so personal data cannot come back by accident. The `contact.anonymized` webhook carries the anonymized object.
- **What it does not change.** The audit log is append-only (database grants) and serves accountability; it keeps earlier entries, which may contain the old values. The anonymization's own audit entry and events contain only the result (no `before`), and the lead updates carry only a reason. Free text in activities and assistant chats is not rewritten (it cannot be done reliably); the export lists it for an Admin to review. The operations guide documents both as retention exceptions.
- **The export is audited** (`contact.personal_data_exported`) and served as an attachment with `Cache-Control: no-store`. A new permission `gdpr.manage` (Admins) lets the UI show the tools.
- **TOTP two-factor sign-in.** RFC 6238, 30-second steps, one step of tolerance, and the accepted step is stored so a code works once. Secrets are encrypted with `APP_ENCRYPTION_KEY` (as webhook secrets); ten recovery codes are shown once and stored as SHA-256 hashes. Wrong codes count towards the account lockout like wrong passwords.
- **Two-step sign-in without a half-session.** A correct password on an account with two-factor sign-in returns `401 auth.mfa_required` and an HMAC-signed, five-minute pending token in an `HttpOnly`, `Secure`, `SameSite=Strict` cookie limited to `/api/v1/auth/login`. Only `POST /auth/login/mfa` reads it; the session is created after the code. No session row exists before that.
- **Enforcement for Admins.** The runtime setting `mfa_required_for_admins` marks the principal of an Admin without two-factor sign-in as `mfa_setup_required`; the permission dependency then refuses every route except `/me`, `/system/info`, sign-out and enrolment (`403 auth.mfa_setup_required`), and the UI sends the Admin to their profile. Admins cannot turn it off while it is required (`403 auth.mfa_enforced`).
- **Lost device.** `python -m app.cli reset-mfa --email …` switches it off for one user and ends their sessions; audited as `user.mfa_reset` with no actor. There is no API for it, so a stolen Admin session cannot remove another Admin's second factor.
- **Security pass findings** (`docs/security/asvs-l1.md`): `/api` responses get `Cache-Control: no-store` unless a route sets its own; the toast library's injected stylesheet is allowed in the CSP by hash (two hashes, guarded by a Playwright check); a concurrent duplicate user creation now returns `409` instead of `500`. Accepted deviations: no `__Host-` cookie prefix (the cookie is limited to `/api`), anonymization confirmed by a typed word rather than the password, search terms in query strings (not logged), common-password list instead of a breach corpus, no malware scan (uploads are parsed, never stored).

## Consequences
- New personal data in a future module needs a provider (and an anonymizer if it should be cleared); the export tests show the pattern.
- Restoring a database backup taken before an anonymization brings the personal data back; the operations guide says to re-apply anonymizations after a restore (they are listed in the audit log).
- A sonner upgrade changes the CSP hash; the security journey fails until the Caddyfile is updated.
- Changing `APP_ENCRYPTION_KEY` makes two-factor secrets unreadable: affected users must be reset with the CLI.
